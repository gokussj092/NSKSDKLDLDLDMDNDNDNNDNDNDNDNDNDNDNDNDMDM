## Bug de presentación .ehi direct_v2r — 2026-11-15

Caso real: clave cloud EFvcmv34, perfil `tunnelType: direct_v2r`, core xray, con la configuración V2Ray completa en el campo `v2rRawJson` (2 inbounds, 4 outbounds). La descarga cloud (método del servidor, `decoders/Python/HTTPINJECTOR_CLOUD.py`) y el descifrado (AES-CBC L1/L2 + XXTEA externo, Argon2id + ChaCha20-Poly1305 interno) funcionan COMPLETOS: el JSON interno tiene 49 campos y el `v2rRawJson` íntegro. No es un error de descifrado.

Causa raíz (app cliente, Kotlin): `ResultPresentation.extractStandaloneJsonObject` (`android/app/src/main/java/com/ghostdeveloper/spdecode/ResultPresentation.kt`) buscaba la primera línea que fuera exactamente `{` en el texto renderizado y la trataba como un documento JSON suelto. El campo `v2rRawJson` es un string JSON multi-línea, y su primer inbound empieza con una línea `    {`; la función extraía solo ese objeto (tun-inbound) y descartaba todo lo demás. La copia JSON de Telegram mostraba por eso únicamente el inbound `tun-inbound`.

Corrección (local, sin push): la función lleva ahora `insideField`, que se abre al ver una línea de campo (regex `sourceLine` existente) y se cierra al ver una línea decorativa (`decorativeLine` / `decoratedHeading` existentes). Solo una línea `{` con `insideField == false` se considera inicio de documento. Esto preserva el caso legítimo (documento JSON suelto antes de cualquier campo, o tras el separador decorativo) y salta las `{` dentro de valores multi-línea. Ninguna otra conducta cambia. Prueba de regresión instrumentada: `android/app/src/androidTest/java/com/ghostdeveloper/spdecode/ResultPresentationInstrumentedTest.kt` (fixture sintético, sin valores reales).

Segundo bug (script Python, separado): `decoders/Python/HTTPINJECTOR_CLOUD.py` llamaba a `ehi.decode_ehi(...)` y `ehi._format_ehi_document(...)`, que no existen en `HTTPINJECTOR.py` (la API actual es `EHIDecryptor.execute(bytes) -> str` y `run(bytes) -> str`); la ruta cloud de Python fallaba siempre con `AttributeError`. Corregido para usar `ehi.run(adapter)` y devolver el texto formateado; el audit sigue registrando transport/app_version/config_ciphertext_sha256/ehi. El módulo hermano `HTTPINJECTOR_EMOJI.py` tenía la misma llamada obsoleta y se corrigió igual. Además, `fetch_response` ahora convierte el `IncompleteRead` de urllib (respuesta chunked truncada, ~45–53 KB) en un `CloudError` explícito con el workaround (curl + `--response`).

Verificación: simulación fiel del pipeline (`~/workspace/http-injector-ehi/simulate_display.py`, fuera del repo) reproduce el bug exactamente con el archivo real y confirma que con la corrección el pipeline entrega los 49 campos con `v2rRawJson` íntegro. El script `tools/check_display_extraction.py` reproduce lo mismo sobre el fixture sintético (7/7 comprobaciones). El script cloud corregido, con `--response` sobre la respuesta guardada, produce el resultado completo sin `AttributeError` (49 campos; HMAC verificado). Kotlin NO se compiló aquí (sin Android SDK en la VM); la validación real es por CI tras el push, que no se hizo.

Límites: los datos reales del archivo EFvcmv34 (host, contraseña trojan, .ehi, respuesta cloud) quedan solo en `~/workspace/http-injector-ehi/`, fuera del repo. El expediente usa solo el fixture sintético. El transporte urllib sigue siendo frágil (IncompleteRead intermitente); el workaround documentado es curl + `--response`.
