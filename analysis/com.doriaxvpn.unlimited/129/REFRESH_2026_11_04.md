# Actualización automática de URL y contraseña — 2026-11-04

**Implementada y verificada en el script de HTTP Conexión y en el broker Cloud.** Sustituye la limitación anterior de mantener URL/contraseña fijadas a la observación del template 17. La investigación inicial se conserva como historial.

## Comportamiento operativo

`server_catalog_decoder.py`, ejecutado sin argumentos, consulta el cliente Firebase de build129, obtiene juntos `ockla_url` y `gretta_pass`, descarga el catálogo con los headers originales y usa esa contraseña para abrir la capa exterior. No requiere ejecutar el probe de investigación ni editar constantes manualmente. Archivo y --stdin conservan compatibilidad con ciphertexts históricos; también aceptan el sobre interno versionado con su contraseña explícita.

El broker Node ejecuta el mismo protocolo mediante HTTPS con DNS público y conexión fijada a IPv4/TLS. No es la API Admin: usa las opciones públicas del cliente Android extraídas de la APK verificada, un ID analítico nuevo y tokens emitidos realmente por FIS. No fabrica Integrity/App Check ni reutiliza tokens de otro usuario. La instalación temporal se intenta eliminar al terminar; sus tokens viven solo en memoria y no se escriben a disco ni a Git. La eliminación es best effort si hay errores; en las verificaciones reales fue HTTP 200.

La pareja se conserva en memoria durante **una hora** por proceso; solicitudes simultáneas de Node comparten una sola consulta. Tras vencer, se actualizan ambos valores de forma conjunta. Un fallo de descarga o descifrado fuerza una sola consulta nueva y un reintento. No se vuelve a `/Update`, a un asset o a la contraseña antigua si Firebase falla o carece de parámetros. Los fallos de Firebase tienen una espera de 60 segundos para evitar una tormenta de consultas.

Solo se aceptan URLs HTTPS canónicas de `raw.githubusercontent.com`, sin credenciales, query ni fragment. Pueden cambiar ruta y repositorio dentro de ese host aprobado. Un cambio a otro dominio exige revisar la allowlist; las URLs arbitrarias del cliente siguen prohibidas. Los tokens de Google nunca se envían al updater. El agente original, headers de caché y timestamp nocache permanecen.

## Contrato con el descifrador

Node entrega al worker un sobre privado `spdecode-http-conexion-config-v1` con exactamente `kind`, `passwordBase64` y `catalogBase64`. Su tamaño total máximo es 8 MiB; no se trunca. El worker continúa sin red, no consulta Firebase ni recibe sus tokens. La contraseña se pasa como argumento de la operación, sin modificar globals, por lo que dos peticiones con contraseñas distintas no se mezclan. La clave de campos GCM permanece como constante propia del formato: `gretta_pass` corresponde a la capa exterior, no a una clave GCM nueva.

La respuesta pública mantiene únicamente el JSON descifrado habitual; no incorpora el sobre interno, tokens ni contraseña de formato. CBC exterior sigue sin autenticidad; se verifican todos los tags GCM de los campos definidos.

## Evidencia real y sintética

Se volvió a descargar el XAPK exacto 129: mismo SHA256 `5ac95f906ec055945ed15172c186ebfcf3f89cbb0c0eff787c89f7d514a21a08` y base `d55c4ce6181ccd82b1846fac4a2c2298b6e5f6e807b07509c84cfe654b777d82`. No se ejecutó la APK ni se repitió la decompilación. Los recursos públicos Firebase y el certificado se extrajeron de ese base mediante `tools/refresh/extract_options.py` y se guardaron como opciones del backend; no son credenciales Admin.

El probe histórico repitió FIS/Remote Config/DELETE con 200/200/200, template 17. El CLI operativo, sin argumentos ni configuración privada externa, también descargó y descifró realmente. `tools/refresh/verify_auto.py` probó otra pareja real: 200/200/200, catálogo107, 244 servidores, 5.325 campos GCM / 5.299 valores distintos, 4.311.432 bytes de entrada. SHA256 `582549fb87e8303010dc332ef770002e2c0e2bd9cc52b0542ff89d4c96522323`. El documento entero coincide con JCA independiente, CLI y worker aislado; el sobre mide 5.748.670 bytes. La contraseña real actual aún coincide con la anterior; no se afirma una rotación real que no ocurrió.

La rotación se verificó con un fixture JCA ficticio cifrado con una contraseña nueva: el valor antiguo falla y la pareja nueva pasa en el worker real. Tests de Node simulan cambio de ruta, contraseña, expiración, peticiones simultáneas, fallo persistente, borrado temporal, bloqueo de destinos no aprobados y un único reintento a través del gateway autenticado.

Resultado final: **27 Python + 172 Node aprobadas** (18 de HTTP Conexión, 9 de regresión Genis). Node real queda `NETWORK_UNAVAILABLE / REMOTE_PROVIDER_UNAVAILABLE` en este ejecutor antes de completar el transporte. El replay con pareja/bytes/resultados reales es explícitamente `SIMULATED_HTTP_REAL_CONFIG_PAIR_AND_BYTES`; no sustituye la prueba de transporte Node en VPS.

## Reproducción y revisiones

Desde la raíz, usando el venv fijado en requirements.lock.txt:

```sh
curl -sS -L --fail --max-time 240 -o private/http-conexion-refresh/HTTP-Conexion-129.xapk 'https://d.apkpure.com/b/XAPK/com.doriaxvpn.unlimited?versionCode=129'
$PY analysis/com.doriaxvpn.unlimited/129/tools/prepare.py private/http-conexion-refresh/HTTP-Conexion-129.xapk private/http-conexion-refresh/unpacked
$PY analysis/com.doriaxvpn.unlimited/129/tools/refresh/extract_options.py private/http-conexion-refresh
$PY decoders/Python/apps/HTTP_Conexion/server_catalog_decoder.py > private/http-conexion-refresh/automatic.json
$PY analysis/com.doriaxvpn.unlimited/129/tools/refresh/verify_auto.py private/http-conexion-refresh
$PY analysis/com.doriaxvpn.unlimited/129/tools/refresh/run_checks.py private/http-conexion-refresh/checks
node analysis/com.doriaxvpn.unlimited/129/tools/probe_node.mjs --real private/http-conexion-refresh/node.bundle
node analysis/com.doriaxvpn.unlimited/129/tools/probe_node.mjs --replay private/http-conexion-refresh/automatic.bundle private/http-conexion-refresh/worker.json
$PY analysis/com.doriaxvpn.unlimited/129/tools/refresh/finalize.py private/http-conexion-refresh
```

El probe histórico adicional requiere `recipe.json` privado; se usó la receta de formato ya verificada para comparar sus defaults, no para configurar el CLI operativo. Los valores privados no se copian a Git. Los scripts de verificación previos conservan sus interfaces: reconocen el nuevo sobre y la contraseña de esa operación. El replay antiguo con ciphertext crudo busca la pareja privada en `firebase-effective.json` junto a la entrada, o en un cuarto argumento explícito.
